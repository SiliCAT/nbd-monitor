# NBD Close Exchange：双端退出事实交接与通信终止设计

- **版本**：v0.1（长期设计契约，v0.0.1 已实现下述裁剪版）
- **日期**：2026-11-26
- **项目**：SiliCAT/nbd-monitor
- **设计基线**：v0.4.2-M0，GitHub `main` 提交 `174a5b101c92ab95202cf0007dd83a205cc0589a`（本轮讨论所依据的源码版本）
- **设计范围**：close 语义、双端事实交接、通信终止契约 E01～E12、E08 专项细则、末端时间契约 W01～W09。

> 核心目标：服务端能够直接拥有每个 Run 的最小完整退出档案；Prometheus 只读取服务端，Grafana 以独立 Run 为单位进行逐轮退出结果交叉分析。

## v0.0.1 实施范围

下列规则用于首版脚本与实机验收。§1～§12 保留长期契约、字段候选和扩展用例。

- **唯一正常退出条件**：同一 Run 的原生 detach 成功、客户端确认设备已解除、服务端确认 QEMU 正常退出且导出资源已释放，并在服务端截止前完成确认和保存。异常、证据缺失及超时均按失败收口，保留原因和已有事实。后到的退出证据可以补记，已保存的失败判定继续有效。
- **最小交接**：客户端用 `close` 报告最终本地事实。仍在等待 QEMU 时，服务端回 `waiting`；双方满足正常退出的事实条件后，服务端回 `ready` 和 Run ID。客户端发 `confirm` 回报该 Run ID；服务端提交成功记录后回 `complete`。该 Run 只有一个用于确认的最终服务端结论。末次 ACK 丢失时，客户端记录未确认，服务端保留已提交的结果，在对应运行记录仍可读取时可以重放同一确认。
- **截止与准入**：服务端从首次有效 close 或 QEMU `finish` 取较早者开始计时，120 秒内完成交接及服务端判定。到期收口为失败并阻断新准入，等待人工核实。客户端从 `disconnect` 起最多主动通信 150 秒，控制请求超时则提前结束。期限到达后，服务端仍可报告当前 Session 的失败原因或重放已保存的成功确认。
- **保存范围**：双端运行状态保存在 `/run`，服务端保存 ACK 确认本次开机的状态文件已原子替换。整机重启使旧 Session 和阻断失效。逐轮诊断进 Journal，其跨重启保留取决于系统配置。

准入、systemd 接入和验收范围见 [最小实机部署设计](MINIMAL-DEPLOYMENT-DESIGN.md)。

## 1. 设计背景与目标

### 1.1 以 Run 为中心，而不是以发布端口为中心

本项目的首要监控目标不是发布端口的当前可用性，而是每个独立运行轮次的退出可靠性，尤其是已结束轮次的退出结果及其异常分布。

- Run ID 是服务端运行轮次的身份；Session ID 用于双端关联。
- port、export、client 是 Run 的属性与聚合维度，而非历史记录的唯一索引。
- `current` 只指向当前轮，不代表所有历史轮次。
- 已结束 Run 的双端事实应保存到对应的现有 `.state` 记录。历史导出窗口与保留策略另行确定；不能只依赖 `current` 或 `last_finished` 推断全部历史结果。

### 1.2 现有设计的偏差

M0 客户端只有在确认本地设备解除后才发送 `op=close`、`session`、`zero=yes`。当原生 detach 未能解除设备、补做禁用或失败、设备状态未知时，客户端可能直接错误退出而一次 close 都不发送。服务端虽已支持解析 `zero=no/unknown`，现有客户端却不发送这两种值；服务端现有 close 状态转换也不能直接套用于新语义。

这造成两类信息缺口：

1. 客户端最有诊断价值的异常退出事实可能完全没有到达服务端。
2. 正常路径中，原生 detach、补做结果及实际收到的服务端结论也没有完整进入服务端 Run 档案。

M0 已经取得大量必要事实，应优先解决信息交接问题，而非扩大现场采集。

### 1.3 预期分析能力

应能独立交叉分析：原生 detach 是否执行及结果、本地设备解除结果、补做配置与实际结果、服务端 QEMU 退出事实、退出协商结果、Reset 配置与结果、双端事实交接结果及证据缺失情况。A1（未执行原生 detach）、A2（执行但本地未确认解除）、A3（本地已解除但服务端未正常收尾）是诊断维度，不应强制互斥；未知不能冒充失败或成功。

## 2. close 的重新定义

**close 是退出阶段的特殊心跳：它是退出动作序列中的通信事件，不是成功退出状态的证明。**

| 操作 | 业务语义 |
|---|---|
| `previous` | 了解上一轮的退出结果 |
| `register` | 建立本轮身份关联 |
| `heartbeat` | 正常运行阶段的状态维系 |
| `close` | 退出阶段多次、双向、渐进式事实交换 |

只要客户端到达规定的退出阶段、身份有效且能够使用控制通道，就应尽力发送 close；不以设备归零、原生 detach 成功或补做成功为条件。异常、未执行、禁用、未知都是合法报告内容。

客户端首次进入有效退出阶段后尽早发送 close，原则上不等待补做结束。随后的 close 可以携带新确定的事实。退出阶段由 close 取代正常 heartbeat；阶段切换不得依赖设备归零。

服务端应将接收并保存客户端事实、检查自身退出状态、执行原有安全处置三项业务分开。接收 close 或最终报告本身不构成释放镜像、执行快照、强制 detach 或 Reset 的新增授权。

## 3. 三个独立结果与事实边界

| 业务维度 | 含义 |
|---|---|
| Client Exit | 客户端自身退出动作及相关观测的阶段性结论 |
| Server Exit | 服务端自身退出观察、协商及处置的阶段性结论 |
| Close Exchange | 双端规定的最终事实是否完成交接及确认 |

退出成功不等于交接成功；退出失败也不妨碍交接成功。另须区分：**交接完整性（Exchange Completeness）**评价规定的报告是否送达并完成确认，**证据完整性（Evidence Completeness）**评价报告中实际已知事实的充分程度。合法的 `unknown` 可以出现在完整交接的报告中。

每项事实应属于以下类别之一：

- 已确定的历史事实：例如原生 detach 的实际执行结果。
- 时点观测事实：例如本地设备状态、QEMU 是否存活；不得推断其永久不变。
- 阶段性最终结论：本阶段已收口，后续不再等待该阶段动作；不意味着未来不会出现新事件。

## 4. 双向消息及最小档案（字段候选）

本节保留讨论中已形成的字段方向，用于解释通信契约；**不是已冻结的线协议、字段枚举或状态文件格式**。

| 客户端 → 服务端 | 服务端 → 客户端 |
|---|---|
| Session、协议版本、close 序号 | 对应 Session/Run 身份、接收及保存确认、回复关联序号 |
| 原生 detach 是否执行、结果、code/status | QEMU 记录状态、可可靠取得的进程观测状态、exit kind/code/status |
| 原生退出后设备状态、close 时设备状态、zero | phase、exit_result、fault |
| 补做是否启用、结果及次数 | Reset 是否启用、状态及结果 |
| 客户端已有保留异常、报告时间 | 服务端接收时间、阶段性最终标志、事实版本 |
| `client_exit_final`、实际收到的服务端事实版本 | `server_exit_final`、交接结果 |

典型候选控制字段：`close_seq`、`ack_seq`、`client_exit_final`、`server_exit_final`、`server_fact_revision`、`seen_server_revision`。时间字段用于关联记录，不依赖跨主机墙钟一致性；截止计时使用各自单调时钟。

旧版仅支持单行回复、严格字段白名单；不能直接向旧版服务端发送扩展字段并假定兼容。正式协议必须另行定义能力/版本兼容、合法枚举、字段一致性及错误分类。

建议采用 H2 有限事实汇总模式：保存原生退出后的初始事实、首次 close 事实、关键变化事实、最新事实和最终交接快照；不保存无限增长的逐条 close 消息副本。详细过程继续由 Journal 承担。初始异常不得被后续恢复覆盖；最新状态为 unknown 时应如实记录，不能用历史已知状态冒充当前状态。

## 5. 通信终止契约 E01～E12

以下为已认可的总体契约，E09 已按最新 W 系列时间决议修订，替代早期“120s 为客户端通信硬截止”的表述。

| 编号 | 契约 |
|---|---|
| E01 | 双方退出成功不是通信成功的必要条件。 |
| E02 | 双方分别声明自身退出结论是否最终确定。 |
| E03 | 最终事实必须取得明确的接收及保存确认。 |
| E04 | 客户端通过后续 close 确认已收到服务端最终结论。 |
| E05 | 确认必须关联具体报告序号及服务端事实版本。 |
| E06 | 最后一个 ACK 不要求再次确认。 |
| E07 | 重复发送相同报告必须幂等。 |
| E08 | 双端事实交接完整时允许提前结束。 |
| E09 | 到达通信硬截止必须终止主动交换。最新客户端通信上限为 150s，120s 为主要退出业务观察窗口。 |
| E10 | 通信终止不意味着设备或进程已释放。 |
| E11 | 后续实际退出事实仍可完善旧 Run 档案。 |
| E12 | 外部强制终止预算采用 30s 梯度，保留充分余量。 |

## 6. E08 专项契约：提前结束的严格条件

### 6.1 双端最终事实

客户端可在下列条件成立后声明 `client_exit_final=yes`：原生 detach 执行事实已取得或明确无法取得；安全检查已结束；补做已完成、禁用、被阻止或预算耗尽；本阶段最终设备检查已完成；不再有计划中的本地退出动作。设备仍连接或未知并不妨碍声明阶段性最终结论。

服务端可在本阶段退出观察及协商已取得结论、相关处置已完成或明确不执行、不再存在需要继续等待的本阶段动作时声明 `server_exit_final=yes`。QEMU 尚存活且观察窗口未耗尽时，原则上继续等待其可能的自然退出；Reset 禁用不自动等于观察阶段结束。

服务端观察窗口到期应形成阶段性超时结论，即使 QEMU 仍然存活。已授权 Reset 或维护业务尚在进行时如何表达该阶段结论与后续处置状态，需在实施前明确；不得伪造处置完成事实。

### 6.2 完成判定

服务端在同一 Run 上满足以下条件，且成功保存交接完成记录后，方可认定交接完整：

1. 客户端最终事实已确定且已正确关联、保存。
2. 服务端本阶段最终事实已确定。
3. 客户端已通过有效 close 回报实际收到对应的服务端最终事实版本。
4. 当前用于完成交接的客户端报告及服务端事实版本相互匹配。

客户端必须收到与自己的最终报告相匹配的有效完成确认，才能依 E08 提前停止通信。服务端与客户端达到 E08 的时间可以不同。

### 6.3 最简交接序列

```text
Client                                      Server
   |--- Close #1: 客户端最终事实 C ----------->|
   |                                          | 保存 C
   |<-- ACK #1 + 服务端最终事实 S / R8 --------|
   |--- Close #2: 确认实际收到 R8 ------------>|
   |                                          | 保存确认及完成快照
   |<-- ACK #2 + exchange_result=complete -----|
   | 结束主动通信                              | 保留重复请求响应能力
```

若双方事实尚未确定，则在窗口内增加正常 close 往返，直到上述闭环成立或者硬截止。最后 ACK 不再要求 ACK 的 ACK。

若 ACK #2 丢失：客户端在剩余时间内重发原样的 Close #2；服务端幂等响应，不重复计数、不重启窗口、不重开旧业务状态机。客户端到期仍未收到 ACK 时，只能记录末次交接未确认；服务端可能已经拥有完整档案。这是有限请求/响应机制不可消除的认知差异。

### 6.4 事实版本与幂等性

- 新的逻辑报告使用新的 `close_seq`；同一报告的原样重发保持原序号与内容。
- 服务端重要退出事实（进程状态、退出结论、异常及相关处置结论、最终标志）变化时更新事实版本。
- 接收次数、接收时间、通信序号、重复 ACK 等纯通信元数据变化不得推动业务事实版本递增。
- 客户端确认旧事实版本时，若当前应交接的版本已变化，服务端返回新版本，不能据旧确认判定完成。
- 版本核验、最终快照提交及重复识别应有一致的并发保护；同序号不同内容或过期报告的处理规则须在正式协议中定义。
- 交接完成后冻结用于此次确认的事实快照；后续实际生命周期事件补充档案，而不追溯取消已完成的交接或重开主动交换。

### 6.5 E08 细化条款

| 编号 | 契约 |
|---|---|
| E08.1 | 双端分别确定自身退出阶段的最终事实，最终不等于成功。 |
| E08.2 | 仍有待执行或等待的退出业务时，不得提前声明该阶段最终结论。 |
| E08.3 | 服务端必须保存身份匹配的客户端最终事实。 |
| E08.4 | 客户端必须报告实际收到的服务端最终事实版本。 |
| E08.5 | 服务端必须保存最终交接结果并返回确认。 |
| E08.6 | 客户端收到有效最终交接确认后，停止发送 close。 |
| E08.7 | 最终交接确认本身不再要求额外确认。 |
| E08.8 | 已明确的 unknown 不妨碍交接完成。 |
| E08.9 | 重复通信及通信元数据变化不得阻碍终止。 |
| E08.10 | 交接完成后允许补充实际发生的退出事实，但不重新开启通信。 |

## 7. 末端时间安排：120s / 150s / 180s

### 7.1 方案选择

现有控制通道由客户端主动发起、服务端被动响应。若将服务端观察窗口延长到 150s 而客户端在 120s 停止主动通信，服务端最后 30s 形成的新退出结论便无法通过 close 送回客户端，也无法得到客户端的接收确认。

因此采用 **服务端 120s 形成阶段性结论，客户端最长 150s 继续主动交换** 的方案。服务端额外独立观察的价值由后续生命周期记录承担，而不应以此代替终止确认。

```text
参考时间轴（示意：双端计时起点相同）
0s                            120s        150s        180s
|-------------------------------|-----------|-----------|
|  主要退出业务、观察及交换       |
|  客户端持续 Close Exchange     | 最终确认   |
|  客户端 systemd 外部保护预算                          |
                                 ↑           ↑           ↑
                       服务端阶段性结论  通信硬截止   外部超时
```

120～150s 是协议层交接余量；150～180s 是外部停止与清理余量，不能用来继续主动通信。满足 E08 即提前结束，不要求等满任何时间。

### 7.2 W01～W09 时间契约

| 编号 | 契约 |
|---|---|
| W01 | 双端退出业务的主要观察窗口为 120s。 |
| W02 | 客户端作为主动通信方，Close Exchange 最大窗口为 150s。 |
| W03 | 服务端 120s 到期后形成阶段性最终结论。 |
| W04 | 服务端形成最终结论后，仍允许身份匹配的事实查询及最终确认。 |
| W05 | 额外 30s 优先服务于最终事实交接，不重新启动退出业务。 |
| W06 | 满足 E08 时立即结束，不必耗尽 150s。 |
| W07 | 150s 到期后客户端停止主动通信。 |
| W08 | 服务端继续保存随后实际发生的生命周期事实。 |
| W09 | 外部 `TimeoutStopSec` 采用更高一级的 30s 梯度。 |

### 7.3 计时起点与硬截止

前期提出的候选起点为：客户端进入有效 `disconnect` 业务；服务端首次有效 close 或 QEMU finish，取先发生者。原生 detach、卸载等此前业务不包含在该候选客户端计时起点内。

各自使用单调时钟，截止期限一旦建立即不可因重复 close、普通 heartbeat、重试或重连而延长。双方启动时间可能不同：30s 是名义交接余量，不是无条件保证。若首次有效 close 延迟或服务端结论形成延迟，客户端实际剩余确认时间可能不足。需要审核服务端回复中的剩余观察时间、首次报告与计时协调、扫描延迟等，不得用客户端可随意重置截止来弥补。

最后阶段可以继续重试最终事实确认，但不得启动不能在剩余预算内完成的新请求。内部硬截止必须涵盖请求超时、终止清理及必要的退出记录开销；不能因外部 `TimeoutStopSec` 较大而突破内部截止。

### 7.4 外部 systemd 超时与现有参数

| 参数 | M0 基线/原讨论值 | 新设计方向 |
|---|---:|---|
| 客户端补做与 close 共用预算 | 30s | 拆分；补做原有最多 30s/3 次限制暂不扩大 |
| 服务端 `closing_timeout_sec` | 默认 45s | 主要退出观察窗口 120s；控制/处置语义需修订 |
| 客户端主动交换窗口 | 原 30s 收尾预算 | 150s 硬截止 |
| 客户端 monitor `TimeoutStopSec` | 40s | 180s 目标（150s + 30s 外部余量） |
| 服务端 export `TimeoutStopSec` | 180s | 不降低；审查完整 stop/finish/maintenance 路径后按 30s 梯度上调 |
| 服务端维护预算 | 默认 120s | 暂不修改 |
| 单次控制请求超时 | 默认 2s | 保持短超时，候选值沿用 |
| 常规 close 周期 | 原约 1s 重试间隔 | 候选 5s + 关键事件触发，未冻结 |

服务端退出观察与快照维护可能先后消耗各自的预算。270s、300s 是待核算的外部超时候选，而非已批准的具体值。systemd 各停止阶段的实际超时语义、Reset 外层 systemctl stop 超时及其他相关包装超时必须联动审核，不能只替换单个数字。所有外部停止超时按 30s 梯度留余量，但不扩大协议内部窗口。

## 8. 时序与异常终止

### 8.1 正常或异常事实均可提前完成

| 客户端最终结论 | 服务端最终结论 | 通信处理 |
|---|---|---|
| 未确定 | 未确定 | 继续交换 |
| 已确定 | 未确定 | 继续取得服务端事实 |
| 未确定 | 已确定 | 继续交接客户端事实 |
| 已确定 | 已确定 | 进入 E08 最终确认；确认完成即结束 |

双方的结论可以是成功、失败、超时或证据未知。不能因为设备仍连接就拒绝保存最终客户端事实，也不能因为设备已经解除就假定服务端完成。

### 8.2 服务端超时但客户端仍可通信

```text
S+120s   服务端形成阶段性结论：QEMU 仍存活 / closing_timeout
         客户端 close：查询并交换当前事实
         服务端回复：server_exit_final=yes + 对应事实版本
         客户端末次 close：确认实际收到该版本
         服务端保存交接结果并 ACK
         客户端满足 E08，提前结束（若尚未到 C+150s）
```

此例中 `exit_result=incomplete` 与 `exchange_result=complete` 可以同时成立，前者描述退出业务，后者描述事实交接。

若控制通道失联、ACK 丢失无法恢复、客户端硬截止到达或被外部终止，则保存已有事实，未确认部分保留未知。不可恢复的身份/协议错误可以提前终止，无需耗尽 150s；瞬时网络失败在预算内仍可重试。

### 8.3 服务端响应生命周期与旧轮归档

服务端在 120s 形成阶段性结论，不等于关闭控制通道或拒绝所有旧 Run close。应继续响应身份匹配的最终查询及确认，包括完成交接后同一末次报告的必要重试。控制响应依赖独立 control socket 和 Session→Run 索引，不要求旧 QEMU 或 export 服务保持存活。

旧轮诊断事实的迟到补充应严格关联原 Run；不能改变新轮的 `current`，不能重开旧业务状态机，不能重新赋予处置权限。允许补充的范围、期限及历史保留策略需在实施设计中明确。

例如 QEMU 在观察超时后自行退出：同时保留观察截止时 `process_at_deadline=running` / 超时事实与后来的实际 `process=exited` / `exit_epoch`。不得用后来的退出覆盖此前的阶段性异常或冻结的交接结论。

## 9. 结果表达与 Grafana 聚合

交接结果候选：`complete`（规定最终事实已完成交接）、`partial`（已取得部分事实）、`not_received`（服务端未取得有效客户端 close）、`protocol_error`（因身份或协议问题无法完成）。终止原因另行表达，例如 `completed`、`deadline`、`protocol_error`、`unknown`。

上述状态必须注明记录方视角。服务端 `complete` 能证明自身保存了必要事实及客户端对服务端最终版本的确认；不能证明客户端收到了最后一个 ACK。客户端的最后 ACK 未确认，应由客户端自身记录；服务端不能凭空取得该事实。对于无有效身份关联的错误，也不能强行归入任意 Run。

| Run（示意） | 原生/本地退出 | 服务端退出 | 服务端交接结论 |
|---|---|---|---|
| A | 原生正常解除 | complete | complete |
| B | 原生异常、补做恢复 | complete | complete |
| C | 本地未解除、补做禁用 | abnormal | complete |
| D | 已解除 | 残留超时 | complete 或 partial |
| E | 客户端证据未知 | heartbeat_timeout | not_received |
| F | 已解除 | complete | partial（缺少对最终事实版本的确认） |

Grafana 应按独立 Run 计数并按退出时间等维度筛选，不按 Prometheus 样本次数计数。Run ID 解决身份问题，历史导出范围解决采样遗漏问题。应另外展示尚未结束但已超时或残留的异常 Run，避免仅筛选 `finished` 导致遗漏。具体指标命名、标签及保留窗口另行设计。

## 10. 安全边界与持久化约束

- 保留原有原生 detach 顺序和补做安全检查；close 新语义不扩大自动处置权限。
- `zero=no/unknown`、`client_exit_final=yes` 或通信到期不能证明安全解除，不得仅据此强制释放设备、停止 QEMU 或执行快照。
- 原有 `phase=closed`、`exit_result=complete` 的安全含义不得被报告接收成功替代。新版需要隔离事实交接状态与原控制状态机，审核 heartbeat/closing timeout 对 Reset 的影响。
- M0 现有实际运行基线 `detach_enabled=no`、`reset_on_timeout=no` 暂不改变。
- 复用既有现场证据，不新增周期性拓扑扫描、持续抓包或持久化观察系统。
- 不新增持久化日志文件、数据库、客户端落盘队列或独立 `.events` 文件；Journal 继续承担详细证据记录。既有 `/run` 交接文件可作为候选复用对象。
- 服务端既有 `.state` 的有限字段增补属于持久化业务修订，具体字段及落盘规则仍需显式审核批准。保存确认仅代表约定的保存操作成功，不自动承诺断电后的数据耐久性。

## 11. 验收矩阵

| 编号 | 场景 | 预期结果 |
|---|---|---|
| E08-01 | 双端正常退出，最终事实均确认 | 提前结束 |
| E08-02 | 双端异常退出，最终事实均确认 | 提前结束，保留异常 |
| E08-03 | 补做后恢复 | 保留初始失败事实及恢复结果，确认后结束 |
| E08-04 | 客户端已解除，QEMU 仍在观察窗口内 | 继续交换 |
| E08-05 | 服务端已退出，客户端本地动作尚未结束 | 继续交换 |
| E08-06 | 双端结论已确定，但尚未完成交接 | 不满足 E08 |
| E08-07 | 客户端确认旧服务端事实版本 | 返回当前应交接版本，不提前结束 |
| E08-08 | 最后一个 ACK 丢失 | 服务端可能已完成；客户端仍未确认 |
| E08-09 | 末次报告原样重试成功 | 幂等确认后结束 |
| E08-10 | 最终报告存在明确 unknown | 可以完成交接，证据完整度独立评价 |
| E08-11 | 重复 close / 纯通信元数据变化 | 不推动业务事实版本、不妨碍终止 |
| E08-12 | 客户端 150s 到期，交接未完成 | 依 E09 终止，保留已有事实 |
| E08-13 | 交接完成后旧 QEMU 产生新退出事实 | 补充旧轮档案，不重开通信 |
| W-01 | 服务端 120s 超时，客户端仍可通信 | 取得最终超时结论并确认，可能满足 E08 |
| W-02 | 首次 close 延迟导致双端计时不同 | 不延长硬截止；不足时如实记录部分交接 |
| W-03 | 旧 Run 结束后新 Run 启动，旧报告迟到 | 仅影响旧 Run 允许补充的诊断字段 |
| W-04 | zero=no/unknown、最终报告或超时 | 不新增强制处置权限 |
| W-05 | 退出观察与维护/Reset 时间预算叠加 | 外部超时协调，内部通信截止不被放宽 |

优先使用隔离模拟验证消息丢失、重复、乱序、计时差和异常路径；实机验证不得以破坏正在使用的块设备或文件系统为代价。

## 12. 设计状态及后续工作

**已形成的设计方向**：Run-centric、服务端单一指标数据源、close 为退出阶段特殊心跳、多次双向事实交换、E01～E12、E08 细则，以及服务端 120s / 客户端 150s / 外部超时按 30s 梯度的时间方向。

**实施前仍需审核**：

1. 双端计时起点及偏差、到期时最终事实生成与有效确认窗口的协调。
2. 正式消息格式、版本兼容、序号与事实版本、最终报告及重复/乱序处理的精确契约。
3. 客户端 run 与 disconnect 的 heartbeat→close 阶段切换，补做与通信预算安排；5s 周期等候选参数。
4. 服务端状态机隔离，`zero=no/unknown` 以及 Reset/维护进行中或到期时的阶段性结论。
5. 旧轮迟到报告、最终快照冻结、状态字段及持久化增补审批、历史保留策略。
6. systemd 外部超时及关联包装超时的完整核算。
7. 契约验证后再实施 Prometheus 逐轮只读导出及 Grafana 聚合。

本节记录长期契约的后续议题。v0.0.1 的实际行为以文首实施范围为准，真实 systemd、内核 NBD 和文件系统联动仍待实机验收。

---

**设计结论：退出动作可以失败，退出事实仍应尽可能完成交接；服务端先形成阶段性最终结论，由主动通信的客户端保留额外确认窗口，满足 E08 即提前结束，到期则有界终止。通信终止后仍允许服务端完善旧 Run 的实际生命周期事实。**
