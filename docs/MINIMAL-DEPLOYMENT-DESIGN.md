- **英文名称**：NBD Minimal Deployment Design
- **设计版本**：v0.1
- **日期**：2026-11-26
- **项目**：SiliCAT/nbd-monitor
- **工程基线**：v0.0.1，`main` 提交 `944e1639ed5647a8a2b9f5d8a50cad75831c99d6`
- **上位契约**：[CLOSE-EXCHANGE-DESIGN.md](https://github.com/SiliCAT/nbd-monitor/blob/944e1639ed5647a8a2b9f5d8a50cad75831c99d6/docs/CLOSE-EXCHANGE-DESIGN.md)（设计 v0.1）
- **状态**：功能裁剪及实机接入、部署设计已通过审核（控制端口确定为 11120）；未实施、未验收。

> **目标：在完整实现最小 Close Exchange 核心契约的基础上，以尽可能薄的实机接入层构成一个真正可以连接、读写、退出、归档并再次连接的 NBD 系统。**

## 1. 定位与设计原则

核心契约定义逐轮退出事实、双端通信及终止确认；本文定义实现这些契约所需的最小 Linux 接入方式、功能边界和部署验收条件。二者相互配套，不在接入层重复构建业务状态机。

```text
应用与分析层：Prometheus / Grafana（后续独立建设）
                         ↑ 只读导出
核心业务层：Run / Session、统一退出事实、Close Exchange、Run 档案
                         ↑ 事实输入 / 业务调用
实机接入层：systemd、nbd-client、Linux NBD、qemu-nbd、控制 TCP
```

- 继续使用 Bash 和 systemd，不自行实现 NBD 数据协议，不增加常驻组件、数据库或新的生产依赖。
- 以 Run 为分析实体，而非仅观察当前发布端口。正常退出、异常退出及通信交接结果分别表达。
- M0 作为历史技术资产，不作为新版行为兼容规范。可按需复用经过验证的事实采集实现；不恢复其独立观察框架。
- 首个最小系统只承担原生连接、生命周期接入、退出事实交接与诊断，不实施主动故障恢复或镜像维护。
- v0.0.1 当前只是不可部署的工程基底；本文不是安装说明书，不将模板或入口骨架视为已实现业务。

## 2. 首个实机可用版本的功能边界

### 2.1 必须实现的最小业务

| 编号 | 业务 | 最小要求 |
|---|---|---|
| M01 | 原生 NBD 连接与发布 | Debian nbd-client + qemu-nbd；一个真实数据连接可用。 |
| M02 | systemd 生命周期接入 | 启动、停止、原生执行事实交接、socket activation。 |
| M03 | Run / Session 关联 | 每轮唯一身份；旧轮不得混入新轮。 |
| M04 | 运行阶段 heartbeat | 建立登记、监护及明确的退出阶段切换。 |
| M05 | 原生 detach 执行事实 | 区分未执行、成功、失败、信号终止和未知等实际情况。 |
| M06 | 客户端设备事实 | 原生退出后及退出交接阶段的设备状态；保留初始异常。 |
| M07 | 服务端进程及残留事实 | QEMU 退出事实、进程身份与必要的 A3 残留观测。 |
| M08 | Close Exchange | 不以成功解除为前提；多次双向事实交换。 |
| M09 | E01～E12、E08 专项契约 | 完整实现适用于本阶段的终止、版本、幂等及确认机制。 |
| M10 | W01～W09 时间契约 | 服务端 120s、客户端 150s、外部停止预算按 30s 梯度。 |
| M11 | 服务端逐轮退出档案 | 保存同轮双端最小事实及结论；准确表达缺失。 |
| M12 | 下一轮正常接入 | 资源正常释放后重新建立连接，保留旧轮档案。 |

核心契约定义的 `previous` 可保留为最小的上轮结果只读查询；不恢复旧版结果枚举或建立额外恢复机制。是否需要独立 `previous/` 索引、查询是否进入启动路径，由核心实施设计确定，不作为原生连接成功的证明。

### 2.2 已确认裁剪：首个版本不实现

| 业务 | 决议 |
|---|---|
| 客户端主动补做 detach | 不实现动作、补做调度、重试及其专用安全处置模块。 |
| 服务端自动 Reset | 不实现停止旧 export、强制释放、自动恢复监听等主动处置流程。 |
| QCOW2 自动快照 | 不实现。 |
| 快照轮换与删除 | 不实现。 |
| 临时写入模式 | 不实现。 |
| 自动重连 | 不实现。 |
| 自动安装器、自动升级 | 不实现。 |
| 独立云端自动化测试工程、GitHub Actions | 不纳入正式工作项目。 |

不为上述业务预建空函数、配置开关、调度器或专用状态机。不通过其他名义恢复已裁剪的功能。

核心契约中涉及补做、Reset、快照的内容作为将来扩展约束保留。本阶段只如实表达相关能力未实现或动作未执行（正式枚举待定），不得伪造执行结果；补做恢复、Reset/维护预算叠加等专属验收用例延期，不属于当前验收失败项。其余通信、安全与诊断契约仍然有效。

### 2.3 实机首验范围

一台客户端、一台服务端（允许容器）、一个 QCOW2 测试镜像、一个数据端口、一个独立控制端口、一个 NBD 设备、一个普通文件系统。单资源、单客户端、单连接，不支持 swap、多人抢占或多连接协商。

这是首验范围，不要求为此另建一次性架构。端口实例化能力可以保留；多资源、多设备并行验收以后开展。

## 3. 服务端最小接入

### 3.1 数据与控制通道

```text
数据端口（例 10920）                     控制端口（11120）
nbd-export@.socket                       nbd-control.socket
  Accept=no                               Accept=yes
       ↓                                      ↓
nbd-export@.service                      nbd-control@.service
  export PORT → exec qemu-nbd              request → 核心协议处理
  finish PORT → 原生退出事实                 ↓
       ↓                                   对应 Run 档案
  QCOW2 镜像

nbd-scan.timer → nbd-scan.service → scan → 观察与超时结论
```

保留既有 socket activation 的技术方向。qemu-nbd 使用单连接、非 persistent 的原生导出；由原生连接生命周期决定其自然退出，不通过 close 命令强行终止数据进程。

独立控制 socket 的生命周期不得依赖某个 export 进程存活。旧 QEMU 已退出或新 Run 已建立时，仍须能够根据有效 Session 定位旧 Run，处理其最终确认及允许的迟到事实。

### 3.2 最小 systemd 单元与程序入口

| 单元（基底中为 `.in` 模板） | 职责 |
|---|---|
| `nbd-export@.socket` | 数据端口监听。 |
| `nbd-export@.service` | 本轮身份建立、原生导出、原生退出事实取得。 |
| `nbd-control.socket` | 独立控制监听。 |
| `nbd-control@.service` | 有界、单次请求/回复。 |
| `nbd-scan.service` | 读取事实、推进超时结论；无处置动作。 |
| `nbd-scan.timer` | 周期触发扫描；无新增常驻进程。 |

保留 `nbd-server` 的候选入口 `export PORT`、`finish PORT`、`request`、`scan`。入口负责环境适配，调用统一核心业务；不各自实现一套退出判定。

- `export`：取得本轮唯一身份，确认不存在未安全释放的资源占用，再启动 qemu-nbd。不得用新轮覆盖旧轮未释放的事实；无法确认安全时拒绝接入。Run ID 可沿用 systemd Invocation ID 的设计，待身份专项冻结。
- `finish`：取得原生 `SERVICE_RESULT`、`EXIT_CODE`、`EXIT_STATUS` 等事实，保存到对应 Run；实际退出记录与阶段性结论分离。不得仅为等待 E08 而长期占住已死亡的旧 export 服务。
- `request`：校验协议、Session / Run 关联、序号与事实版本，保存并回复。只有保存成功才可确认保存成功；回复写出不代表客户端收到。
- `scan`：处理登记或心跳失联、退出观察到期、尚未收口的历史轮次等。不能仅检查 `current` 而遗漏旧轮；不要求每次全量扫描所有历史档案。具体待处理轮次定位方式另行设计，不预先新增持久化索引。

任何入口均不得因报告异常、观察超时或 E08 完成而自动杀死 QEMU、执行 Reset 或修改镜像。旧进程残留时保留现场，不能通过忽略资源占用来保证重新连接。

## 4. 客户端最小接入

### 4.1 原生生命周期职责

使用 `/etc/nbdtab`、Debian 原生 `nbd@nbdN.service` 和 `/usr/sbin/nbd-client` 负责真实连接及 detach。上层挂载由现有 fstab、systemd automount 或 autofs 管理。本项目不增加挂载管理器，不代替原生 ExecStart/ExecStop，不修改文件系统数据。

`nbd-monitor@.service` 和原生 `nbd@.service.d/` drop-in 是接入基础。v0.0.1 中的 `monitor.conf.in`、`timeout.conf.in` 及 monitor 服务模板仅作为研发参考，最终依赖与超时须验证后落地。原生 hook 的具体文件名、调用入口及启动/退出顺序尚待确认。

### 4.2 启动时间轴（候选接入方式）

```text
monitor 启动、准备候选 Session
     ↓ READY（表示准备完成，不是连接或登记成功）
原生 nbd@ 执行真实连接
     ↓ 原生启动事实 / Invocation ID 交接
monitor 识别真实连接并 register
     ↓ 有效登记
正常 heartbeat
```

建议在 READY 前生成候选 Session，使启动、原生退出观察与通信共享身份。候选 Session 不等于已登记 Session；只有与真实 Run 成功关联后，才能用其发送对应轮次的 close。未登记、身份不明或启动失败时应保留本地事实，不强行将报告关联至任意旧 Run。

由原生 `ExecStartPost=` 直接交接 Invocation ID 是候选简化方案，需实机验证。该 hook 仅提供本地身份事实，不等待远程 register，避免与 READY、原生启动作业和 monitor 形成依赖循环。不得依靠裸 UUID、当前设备名或历史 ExecStop 记录推断本轮身份。

### 4.3 退出时间轴

```text
上层业务停止并安全卸载（由现有系统负责）
     ↓
原生 ExecStop：nbd-client -d /dev/nbdN
     ↓
原生 ExecStopPost：取得并交接原生执行及设备事实
     ↓
monitor ExecStop：disconnect
     ↓
退出阶段接管：停止普通 heartbeat，尽早发送 close
     ↓
必要的设备事实复查、双端事实交换及最终确认
     ↓
满足 E08 或 150s 硬截止 / 不可恢复错误
     ↓
本地退出摘要进入 Journal
```

实际发生的原生动作可能失败、未执行或无可靠记录。退出时间轴是接入目标，不可当作动作一定执行的证据。即使本地设备仍连接或未知，身份有效且控制通道可用时也应尽力交接退出事实；缺失原生证据不阻断 close。不能确认身份时不得冒用会话。

普通 heartbeat 到 close 的切换由明确的生命周期阶段驱动，而不是以设备归零为门槛。处理正在进行的 heartbeat、并行的 run/disconnect、重复 stop 等竞态；旧 heartbeat 不得使退出阶段回退或延长截止。首个版本无补做动作，故退出事实收口无需等待补做循环。

通信成功不证明设备已释放、文件系统一致或故障已恢复。上层业务尚未安全卸载时不得为测试而强行 detach。

## 5. 时间及终止契约在实机中的映射

| 时间项目 | 初步部署设计 |
|---|---|
| 服务端阶段性退出观察 | **120s**，到期形成结论，不触发主动处置。 |
| 客户端主动 Close Exchange | **150s** 硬截止，满足 E08 即提前结束。 |
| 客户端 monitor `TimeoutStopSec` | **180s** 目标，外部余量不用于继续主动通信。 |
| 服务端 export `TimeoutStopSec` | 保留 180s 模板起点，核算实际停止路径后确认。 |
| 正常 heartbeat 间隔 / 失联阈值 | 10s / 30s 候选。 |
| 常规 close 间隔 | 5s + 关键事实变化触发，候选。 |
| 单次控制请求 | 2s 候选；须与接收、锁、回复及清理预算协调。 |
| 扫描周期 | 5s 候选；不因此延长已建立的观察截止。 |

双端计时起点及偏差按核心契约 §7.3 继续审核。候选：客户端进入有效 disconnect，服务端首次有效 close 或 QEMU finish 两者取先。卸载与原生 stop 属于此前阶段；180s 是 monitor 的外部停止预算，不是整个关机耗时上限。

使用各自主机单调时钟。重复消息不得延长截止。服务端到期判定可由请求入口与 scan 共同推进，必须以真实截止判断；扫描实际发现时间与截止时间不得混淆。若处理延迟、首次报告延迟或控制通道中断导致名义 30s 交接余量不足，仍须在 150s 停止主动交换并准确标注部分交接。

服务端 120s 到期只冻结阶段性结论，不关闭独立控制通道，不阻止末次 ACK 的幂等响应。后续 QEMU 退出事实可补记原 Run，不覆盖历史超时事实或重开已完成的通信。

本阶段取消补做、Reset、镜像维护预算，无需为它们预设 270s/300s 等外部超时。所有正式超时仍需结合实际 systemd 阶段语义验证。

## 6. 极简配置、状态和日志

### 6.1 配置候选

只暴露实机接入所需的最少参数，不设计尚无用途的开关或多层覆盖。以下仅为示例，不是已冻结格式，也不用于修改现有生产配置。

服务端 `/etc/nbd-server.conf`：

```ini
[10920]
image = /srv/nbd/test.qcow2
export = TEST
```

客户端 `/etc/nbd-monitor.conf`：

```ini
[global]
client_id = test-client
control_port = 11120
```

原生 `/etc/nbdtab`：

```text
nbd0 192.0.2.10 TEST port=10920
```

192.0.2.10 为文档示例地址；实机使用专用测试服务端地址及确认空闲的设备和端口。数据服务器、端口和 export name 优先从原生配置取得，控制服务器默认使用相同地址为候选。独立控制端口确定为 11120，客户端配置与服务端监听必须一致。

已确定的核心时间契约无需立即配置化。首个版本不解析或提供自动补做、Reset、快照、临时写入开关，不接受旧版配置并默默忽略可能影响安全的功能参数。正式配置校验及迁移策略待确定。

### 6.2 客户端状态

使用现有 `/run/nbd-monitor/<device>/` 或等价临时目录保存会话上下文、运行/退出事实和必要的锁。文件数量服从写入者、生命周期和并发安全，而非数量指标。原生 hook 的交接记录可以独立保存；不新增客户端持久化队列、日志文件或真实文件系统状态。

临时目录和身份关联须防止跨启动、跨设备、跨 Session 串写。Journal 作为详细现场证据来源；缺少有效交接记录时汇报 unknown。

### 6.3 服务端 Run 档案

优先复用原有结构（候选）：

```text
/var/lib/nbd-server/
├── resources/<port>/
│   ├── current
│   └── runs/<run-id>.state
└── sessions/<session-index>
```

历史 `previous/` 索引按实际查询需要决定。Run 是历史分析单位；`current` 只服务于资源定位与占用保护，不能成为所有历史事实的唯一来源。

身份匹配、并发互斥、原子保存与 ACK 必须正确关联。旧轮档案不因新轮启动、晚到消息或重试被覆盖；已确认快照与后续生命周期事实须区分。保存 ACK 表示约定的保存操作成功，不自动承诺掉电耐久性。

**持久化审批边界：** 本文不授权新增持久化文件、字段、索引或写入方式。实现 Run 档案前，必须先审核核心事实字段、落盘规则、历史保留及旧版状态隔离/迁移；不将旧档案直接解释为新协议的已确认事实。详细日志进入 Journal，不另建日志文件、数据库或 `.events` 文件。

## 7. 极简实机部署流程

### 7.1 部署前提

- 核心协议、身份与档案格式已确定，业务代码完成必要的云端逻辑验证。
- 使用隔离的测试镜像、端口、设备及挂载点；确认无活动生产会话与文件系统占用。
- 核对目标 Linux 的 systemd、内核 NBD、Debian nbd-client 及服务端 qemu-nbd（通常由 qemu-utils 提供）。不以普通用户 PATH 查找失败判断系统管理工具未安装。
- 控制通道在没有认证和加密的情况下仅用于受控可信网络；限制数据和控制端口的可达范围，不直接暴露到互联网。Session 关联不等于身份认证。
- 双端使用匹配的新版实现。旧版线协议兼容不属于本阶段要求；禁止将新版一端接入未确认兼容的生产旧版。

### 7.2 人工部署步骤（设计流程，不是当前可执行安装命令）

| 顺序 | 服务端 | 客户端 |
|---|---|---|
| P1 | 准备依赖及隔离测试镜像 | 准备依赖、确认 NBD 设备可用 |
| P2 | 部署已实现的 `nbd-server` | 部署已实现的 `nbd-monitor` |
| P3 | 部署审核后的正式 systemd 单元 | 部署审核后的 monitor 单元和原生 drop-in |
| P4 | 填写镜像、export 及监听配置 | 填写 monitor 配置和原生 nbdtab |
| P5 | daemon-reload，检查单元和配置 | daemon-reload，检查依赖和配置 |
| P6 | 启动控制/数据 socket 和 scan timer | 通过原生 nbd@ 建立连接 |
| P7 | 检查 Run 与 Session 登记 | 检查设备，挂载测试文件系统，执行受控读写 |
| P8 | 观察退出与 Run 档案 | 停止上层业务，卸载，再停止原生 nbd@ |
| P9 | 确认旧资源释放及历史档案保留 | 重新连接，验证数据及新轮关联 |

按现有根文件系统映射目录进行最小人工部署，不开发安装器。只有相应实现与单元通过审核后，才将 `.in` 模板转为正式部署文件。不允许直接复制整个 v0.0.1 基底到生产根目录；特别禁止在活动挂载期间替换或重启 monitor、原生 nbd@ 或 export 服务。

部署失败时停止在隔离环境中诊断，保留证据。未确认旧资源安全释放，不继续启动新导出、不覆盖镜像。历史生产版本可从 `archive/v0.4.2-M0` 获取；回退应在安全停机且确认无活动连接后进行，不能混用状态文件及协议。

## 8. 最小实机接入契约 MD01～MD15

| 编号 | 契约 |
|---|---|
| MD01 | 使用原生 nbd-client 与 qemu-nbd，不重新实现 NBD 数据通道。 |
| MD02 | 使用 systemd 管理生命周期。 |
| MD03 | 数据通道与控制通道独立。 |
| MD04 | 控制通道不依赖旧 export 进程存活。 |
| MD05 | 首验限定单资源、单客户端、单连接。 |
| MD06 | 通过原生单元取得启动与退出事实，可靠关联本轮身份。 |
| MD07 | 实机接入层不得重复实现核心状态机。 |
| MD08 | 保留上层安全卸载、原生 detach 的基本顺序；缺失或异常须如实记录。 |
| MD09 | 首个版本不实施主动补做 detach 和自动 Reset。 |
| MD10 | 首个版本不实施自动快照及其它镜像维护。 |
| MD11 | 客户端仅使用临时状态和 Journal。 |
| MD12 | 服务端优先复用现有 Run 档案基础设施，具体落盘增补须先批准。 |
| MD13 | 不新增常驻组件及生产依赖。 |
| MD14 | 标准路径、最小配置、人工部署。 |
| MD15 | 云端尽量消化可验证的问题，本地完成真实环境验收；不建立独立云端自动化工作项目。 |

MD01～MD15 及 §2.2 的功能裁剪已经通过审核；具体实现候选及 §11 待确认事项仍须在实施前验证或确定。

## 9. 验收与研发分工

### 9.1 云端可消化的验证

不单列正式自动化工程，不引入 CI；在研发当次环境能力允许时，尽量直接验证实际 Bash 代码。可使用临时隔离目录、样本、替代底层命令和真实 loopback TCP 等方式。

| 验证范围 | 要求 |
|---|---|
| 配置/消息/原生执行记录解析 | 正常、非法、缺失、冲突、unknown 等边界。 |
| Close Exchange | E01～E12、E08、序号/版本匹配、重复/乱序、ACK 丢失、保存失败。 |
| 时间 | 内部截止、不同计时起点、单次请求阻塞、最终确认窗口。 |
| 并发与状态 | 锁、原子保存、新旧 Run 隔离、冻结快照、迟到补记。 |
| 异常路径 | 注入 A1/A2/A3 事实及控制通道故障，验证处理而非声称复现真实成因。 |
| systemd 模板 | 环境允许时进行离线语法及依赖审查，不替代真实生命周期验收。 |

验证结果应注明真实执行、模拟或未测试。云端不能取得的真实 NBD 内核、完整 systemd、QEMU 与文件系统联动证据由实机补足，不将模拟通过视作实机通过。

### 9.2 实机验收矩阵

| 编号 | 验收项目 | 通过条件 |
|---|---|---|
| D01 | 服务端监听 | 控制/数据 socket 与 scan 正常启用，数据连接触发正确导出。 |
| D02 | 原生连接 | 原生 nbd@ 正常建立测试 NBD 设备。 |
| D03 | 双端关联 | 原生 Invocation、Session、Run 正确关联；无历史记录冒用。 |
| D04 | 上层业务 | 测试文件系统正常挂载、读写、卸载。 |
| D05 | 原生退出事实 | 原生执行记录及 post-stop 设备事实可可靠取得，缺失如实标注。 |
| D06 | 阶段切换 | 正常 heartbeat 切换到 close；无退出阶段回退。 |
| D07 | 正常 E08 | 双端最终事实、版本、保存与最终确认满足契约，提前结束。 |
| D08 | 异常报告 | A1/A2 或未知事实不会仅因设备未归零而被禁止发送；验证无主动补做。 |
| D09 | Run 档案 | 逐轮事实完整或明确缺失，退出结果与交接结果分离。 |
| D10 | 下一轮 | 旧资源正常释放后再次连接成功，Run 身份不同。 |
| D11 | 跨轮隔离 | 旧轮最终确认/重试不污染新轮，独立控制通道继续可用。 |
| D12 | 实际重启 | 正常重启后依据原生配置恢复连接及文件系统使用，验证 shutdown 时序和网络可用性。 |
| D13 | 安全保留 | 失联、残留或超时时不自动处置；未安全释放时拒绝不安全的再次导出。 |
| D14 | 数据完整性 | 正常退出并重新连接后，预先写入的测试数据校验一致。 |

此外，必须验证 W01～W09 的真实停止预算及控制通道寿命；超时观察的事实和后续实际退出事实可以同时保存。对 A1/A2/A3 真正异常成因的捕获，优先等待真实现场或使用隔离可丢弃资源进行安全实验，禁止人为破坏活动生产连接。无法安全复现的场景标注为未实机验证，不冒称已验收。

### 9.3 最小可用性判定

正常实机闭环：监听 → 原生连接 → 登记与 heartbeat → 挂载读写 → 卸载 → 原生 detach → 双端 Close Exchange → 对应 Run 档案 → 再连接与数据校验。

至少完成两个独立正常 Run 并核对历史档案不被覆盖（建议首验方法）；D12 重启链路单独验证。核心异常与终止规则应先在可控环境验证；真实异常专项结果分别记录。任何安全不变量失败均阻止部署验收通过。异常样本中交接可失败，但必须准确记录原因和已有事实，不以自动恢复作为通过条件。

## 10. 指标分析的建设顺序

第一个可运行闭环以服务端 Run 档案可用为验收终点。第二个应用闭环为：Run 档案 → 服务端只读导出 → Prometheus → Grafana，以独立 Run 进行逐轮退出结果交叉分析。

后者是总体目标，暂不作为第一个实机接入闭环的前置依赖。指标导出不增加客户端 exporter，不改变 NBD 连接/退出动作，不先行冻结指标名、标签或历史保留窗口。

## 11. 实施前尚待确认

1. 统一身份生命周期、候选 Session 生成与登记失败处理；原生 `ExecStartPost=` 直接身份交接及 `ExecStopPost=` 证据关联的实机可行性。
2. `run` / `disconnect` 阶段切换与并发保护；原生启动失败、退出 hook 缺失时的事实表达。
3. 最小正式消息与事实模型；明确未实现的处置能力如何表达，不携带无业务价值的冗余字段。
4. Run 档案具体持久化字段、保存确认、旧档案隔离与历史保留审批；历史待收口 Run 的定位方式。
5. 双端计时起点、扫描延迟及最终确认余量；最终 systemd 依赖、超时和控制 socket 在关机期间的可用性。
6. 最小配置格式、模板转正式单元及首验环境安排。

不再把补做、自动 Reset、快照等远期业务作为以上设计完成的前置条件。本文不修改上位核心契约文件；如其中的候选字段或扩展业务与当前范围存在差异，以已确认的 §2.2 裁剪作为本阶段实施范围约束。

---

**设计结论：最小可用系统不是缩小版的自动恢复系统，而是能够接入真实 NBD 生命周期、尽可能完整交接双端退出事实、保留异常证据并在资源正常释放后继续下一轮的诊断系统。先使核心业务与实机接入闭环成立，再按实际需求扩展恢复能力及指标分析。**
