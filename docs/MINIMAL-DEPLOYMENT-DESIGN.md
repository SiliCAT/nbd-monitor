## v0.0.7 接入增补

遵循上位契约 T03 D01～D07：admit 为轻量预约，复用单次请求保护与 ExecStartPre 启动保护重试同一 Session；未形成 Run 的预约过期记 released/not_started，不永久阻断。reserved close 按设备证据结束、等待原期限或矛盾阻断；已收到 close 不再允许该预约启动导出。保留原生连接只执行一次及实际 Run 保护，不改变 systemd 单元、配置、线协议、权威状态行数和生产依赖。当前仅用于一对一映射和受控网络，迟到连接不能由此机制可靠识别；真实身份准入待专题研究。双端安全空闲升级，候选版待实机验收。历史章节中 admission_timeout 永久阻断及单次 admit 失败处理由本节替代。

## 1. 定位与设计原则

核心契约定义逐轮退出事实、双端通信及终止确认；本文定义实现这些契约所需的最小 Linux 接入方式、功能边界和部署验收条件。二者相互配套，不在接入层重复构建业务状态机。所有接入层时间约束遵循上位契约[超时最小化原则](CLOSE-EXCHANGE-DESIGN.md#总体设计契约超时最小化原则)，新增或保留超时须说明目的、必要性、预算及失败后果。真实关机是退出机制主要验收基准。

```text
应用与分析层：Prometheus / Grafana（后续独立建设）
                         ↑ 只读导出
核心业务层：Run / Session、统一退出事实、Close Exchange、Run 档案
                         ↑ 事实输入 / 业务调用
实机接入层：systemd、nbd-client、Linux NBD、qemu-nbd、控制 TCP
```

- 继续使用 Bash 和 systemd，不自行实现 NBD 数据协议，不增加常驻组件、数据库或新的生产依赖。
- 以 Run 为分析实体，记录正常或失败判定，以及相应的退出事实和交接结果。
- M0 作为历史技术资产，不作为新版行为兼容规范。可按需复用经过验证的事实采集实现；不恢复其独立观察框架。
- 首个最小系统只承担原生连接、生命周期接入、退出事实交接与诊断，不实施主动故障恢复或镜像维护。
- v0.0.1 正常无挂载路径已实机六轮通过；v0.0.2 修订停止边界及日志，仍待本版实机验收。

## 2. 首个实机可用版本的功能边界

### 2.1 必须实现的最小业务

| 编号 | 业务 | 最小要求 |
|---|---|---|
| M01 | 原生 NBD 连接与发布 | Debian nbd-client + qemu-nbd；一个真实数据连接可用。 |
| M02 | systemd 生命周期接入 | 启动、停止、原生执行事实交接、socket activation。 |
| M03 | 准入及 Run / Session 关联 | 同一资源先到先得，获得准入后才执行原生连接。每轮身份独立。 |
| M04 | 运行阶段 heartbeat | 关联服务端 Run、监护会话并在退出时切换。 |
| M05 | 原生 detach 执行事实 | 区分未执行、成功、失败、信号终止和未知等实际情况。 |
| M06 | 客户端设备事实 | 在 `finalize` 中采集原生停止后的设备状态；未知保持 unknown。 |
| M07 | 服务端进程及残留事实 | QEMU 退出事实、进程身份与必要的 A3 残留观测。 |
| M08 | Close Exchange | 不以成功解除为前提；多次双向事实交换。 |
| M09 | 首版退出判定 | 按核心契约文首的唯一成功路径，完成 `close → ready → confirm → complete`。 |
| M10 | 时间契约 | 服务端 120s 判定截止，客户端 150s 通信上限，外部停止预算为 180s。 |
| M11 | 服务端逐轮退出记录 | 本次开机的运行状态在 `/run`，诊断事实进入 Journal。 |
| M12 | 下一轮接入 | 旧轮正常收口且释放资源后接受新请求。失败轮次等待人工核实并解锁。 |

当前资源状态可通过客户端 `nbd-monitor report DEVICE` 查询，历史结果通过 Journal 查询。

不为上述业务预建空函数、配置开关、调度器或专用状态机。不通过其他名义恢复已裁剪的功能。

核心契约中涉及补做、Reset、快照的内容保留为后续扩展。首版验收沿用其安全边界和文首 v0.0.1 交接规则。

### 2.3 实机首验范围

一台服务端、一个 QCOW2 测试镜像、一个数据端口、一个独立控制端口。正常链路使用一台客户端、一个 NBD 设备和一个普通文件系统；准入验收再用第二台受管客户端竞争同一资源。同一资源同时只准入一个客户端和一条数据连接。

这是首验范围，不要求为此另建一次性架构。端口实例化能力可以保留；多资源、多设备并行验收以后开展。

## 3. 服务端最小接入

### 3.1 数据与控制通道

```text
数据端口（例 10920）                     控制端口（11120）
nbd-export@.socket                       nbd-control.socket
  Accept=no                               Accept=yes
       ↓                                      ↓
nbd-export@.service                      nbd-control@.service
  export PORT → exec qemu-nbd              request → 核心协议处理
  finish PORT → 原生退出事实                 ↓
       ↓                                   对应 Run 档案
  QCOW2 镜像

nbd-scan.timer → nbd-scan.service → scan → 观察与超时结论
```

保留既有 socket activation 的技术方向。qemu-nbd 使用单连接、非 persistent 的原生导出；由原生连接生命周期决定其自然退出，不通过 close 命令强行终止数据进程。

控制 socket 独立于 export 进程。QEMU 退出后，当前 Session 仍可交接。新 Run 建立后，尚在保留期内的旧 Session 可以重放已保存的成功确认。

### 3.2 最小 systemd 单元与程序入口

| 单元（正式文件名，待验收） | 职责 |
|---|---|
| `nbd-export@.socket` | 数据端口监听。 |
| `nbd-export@.service` | 本轮身份建立、原生导出、原生退出事实取得。 |
| `nbd-control.socket` | 独立控制监听。 |
| `nbd-control@.service` | 有界、单次请求/回复。 |
| `nbd-scan.service` | 读取事实、推进超时结论；无处置动作。 |
| `nbd-scan.timer` | 周期触发扫描；无新增常驻进程。 |

服务端入口为 `export PORT`、`finish PORT`、`request`、`scan` 和本地操作命令 `unlock PORT SESSION`。各入口共用每资源的状态和锁。

- `export`：在资源锁内复核有效准入，以 systemd Invocation ID 作为 Run ID，再启动 qemu-nbd。数据 socket 保留 `Accept=no`，启动审核按资源执行。所有能访问数据端口的客户端须遵守准入顺序。
- `finish`：取得原生 `SERVICE_RESULT`、`EXIT_CODE`、`EXIT_STATUS` 等事实，保存到对应 Run；实际退出记录与阶段性结论分离。不得仅为等待 E08 而长期占住已死亡的旧 export 服务。
- `request`：处理 `admit`、`status`、`heartbeat`、`close` 和 `confirm`。校验会话及需要确认的 Run，保存结果后回复。
- `scan`：判定当前准入、心跳和退出截止，并清理超出重放期限的旧轮临时状态。
- `unlock`：人工核实旧进程、镜像和排队数据连接已释放后，按当前阻断 Session 解锁。脚本复查可验证的进程状态，并将解锁记录写入 Journal。

任何入口均不得因报告异常、观察超时或 E08 完成而自动杀死 QEMU、执行 Reset 或修改镜像。旧进程残留时保留现场，不能通过忽略资源占用来保证重新连接。

## 4. 客户端最小接入

### 4.1 原生生命周期职责

使用 `/etc/nbdtab`、Debian 原生 `nbd@nbdN.service` 和 `/usr/sbin/nbd-client` 负责真实连接及 detach。上层挂载由现有 fstab、systemd automount 或 autofs 管理。本项目不增加挂载管理器，不代替原生 ExecStart/ExecStop，不修改文件系统数据。

`nbd-monitor@.service` 和 `nbd@.service.d/monitor.conf` 负责接入原生单元。模板使用 `ExecStartPre=admit`、`ExecStartPost=observe-start` 和 `ExecStopPost=finalize`；依赖和实际调用顺序须在目标机验证。

### 4.2 启动时间轴

```text
monitor 启动并报告 READY
     ↓
原生 ExecStartPre 创建候选 Session，向控制端口申请准入
     ↓ 收到本轮准入确认
原生 ExecStart 执行一次数据连接
     ↓ ExecStartPost 交接本地启动事实
正常 heartbeat
```

控制请求被拒绝、超时或未确认时，客户端以启动失败结束。一次准入只执行一次原生连接；受管客户端通过 `nbd@` 启动，查询走控制通道，数据端口留给获准后的实际连接。原生 `nbdtab` 禁用自动重连和多连接。

### 4.3 退出时间轴

```text
上层业务停止并安全卸载（由现有系统负责）
     ↓
原生 ExecStop：nbd-client -d /dev/nbdN
     ↓
原生 ExecStopPost：finalize，记录 stopping 并采集原生执行及设备事实
     ↓
在 heartbeat.lock 内完成在途心跳与事实交接，尽早发送 close
     ↓
必要的设备事实复查、双端事实交换及最终确认
     ↓
收到最终结果，或因超时、控制错误结束
     ↓
本地 final 原子替换，退出摘要进入 Journal
     ↓
原生停止作业结束；monitor 随后仅清理后台进程
```

实际发生的原生动作可能失败、未执行或无可靠记录。退出时间轴是接入目标，不可当作动作一定执行的证据。即使本地设备仍连接或未知，身份有效且控制通道可用时也应尽力交接退出事实；缺失原生证据不阻断 close。不能确认身份时不得冒用会话。

普通 heartbeat 到 close 的切换由明确的生命周期阶段驱动，而不是以设备归零为门槛。处理正在进行的 heartbeat、并行的 run/finalize、重复 stop 等竞态；旧 heartbeat 不得使退出阶段回退或延长截止。首个版本无补做动作，故退出事实收口无需等待补做循环。

文件系统一致性通过实机读回验收。上层业务尚未安全卸载时不得为测试而强行 detach。

## 5. 时间及终止契约在实机中的映射

| 时间项目 | 首版实现与模板 |
|---|---|
| 服务端退出及交接 | **120s**，到期记为失败并阻断同一资源的新准入。 |
| 客户端主动 Close Exchange | **150s** 上限，收到最终结果或请求超时可提前结束。 |
| 原生 nbd@ / export `TimeoutStopSec` | **180s** 模板预算，实机核验各停止阶段。 |
| monitor `TimeoutStopSec` | **10s**，只清理后台进程。 |
| 准入有效期、heartbeat 间隔 / 失联阈值 | 30s，10s / 30s。 |
| 常规 close 间隔 / 单次控制请求上限 | 5s / 2s。收到 `ready` 后立即确认。 |
| 扫描周期 | 5s，由系统定时器推进，截止仍以保存的时间为准。 |

客户端从有效 `finalize` 起计时，服务端从首次有效 close 或 QEMU `finish` 取较早者。双端使用各自主机的单调时钟。卸载和原生 stop 在客户端通信计时前执行。请求入口与 scan 均检查服务端截止，重复消息不续期。

120s 后保留已保存的结果。QEMU 后来退出时可补记事实，原判定和人工阻断继续有效。

本阶段取消补做、Reset、镜像维护预算，无需为它们预设 270s/300s 等外部超时。所有正式超时仍需结合实际 systemd 阶段语义验证。

原生 stop 作业结束意味着 finalize 已返回或被 systemd 终止，不等于双端退出成功。必须匹配本轮 native Invocation / Session / Run 的 final 与 Journal；缺失或异常终止为未确认。不得在原生 hook 中同步等待 monitor 停止，否则会违反逆序停止依赖。

## 6. 极简配置、状态和日志

### 6.1 首版配置

以下示例对应首版配置模板，供隔离环境验收使用。

服务端 `/etc/nbd-server.conf`：

```ini
[10920]
image = /srv/nbd/test.qcow2
export = TEST
```

客户端 `/etc/nbd-monitor.conf`：

```ini
[global]
client_id = test-client
control_port = 11120
```

原生 `/etc/nbdtab`：

```text
nbd0 192.0.2.10 TEST port=10920
```

192.0.2.10 为文档示例地址。实机使用专用测试服务端地址及确认空闲的设备和端口。客户端从原生配置读取数据服务器、端口和 export name，并连接相同主机的控制端口 TCP 11120。

首版时间值由脚本和单元模板设定。脚本拒绝未知配置项，旧版配置应按首版示例重新填写。

### 6.2 客户端状态

使用现有 `/run/nbd-monitor/<device>/` 或等价临时目录保存会话上下文、运行/退出事实和必要的锁。文件数量服从写入者、生命周期和并发安全，而非数量指标。原生 hook 的交接记录可以独立保存；heartbeat.lock 仅保护单次心跳及 binding/fault 保存，finalize 写 stopping 后等待最多 4 秒并重查事实，超时按失败、不宣称正常。final 为七行：native Invocation、Session、Run（未知为 -）、result、reason、native、device。未确认准入不发送 close，保留失败证据；其他 Invocation 不得冒用旧记录。不新增客户端持久化队列、日志文件或真实文件系统状态。

临时目录和身份关联须防止跨启动、跨设备、跨 Session 串写。Journal 作为详细现场证据来源；缺少有效交接记录时汇报 unknown。

### 6.3 服务端 Run 档案

本次开机的服务端运行记录：

```text
/run/nbd-server/port-<port>/
├── lock
├── current
└── <session>.state
```

`current` 指向该资源当前 Session。服务端以同目录原子替换提交结果，成功后返回确认。旧轮移出 `current` 且终态已满 150 秒后，scan 可清理其临时记录。诊断历史在 Journal，跨重启保留取决于系统配置。control 和 scan 单元设置 LogLevelMax=notice、SyslogLevel=notice；不调整心跳或扫描时限，不抑制脚本退出事实。

单元重启保留 `/run` 中的当前状态和阻断。整机重启后旧 Session、期限和阻断全部失效，服务端重新按当前资源开放准入。长期持久化档案及旧版状态迁移留待后续评估。

## 7. 极简实机部署流程

### 7.1 部署前提

- 核心协议、身份与档案格式已确定，业务代码完成必要的云端逻辑验证。
- 使用隔离的测试镜像、端口、设备及挂载点；确认无活动生产会话与文件系统占用。
- 核对目标 Linux 的 systemd、内核 NBD、Debian nbd-client 及服务端 qemu-nbd（通常由 qemu-utils 提供）。不以普通用户 PATH 查找失败判断系统管理工具未安装。
- 控制通道在没有认证和加密的情况下仅用于受控可信网络；限制数据和控制端口的可达范围，不直接暴露到互联网。Session 关联不等于身份认证。
- 双端使用匹配的新版实现。旧版线协议兼容不属于本阶段要求；禁止将新版一端接入未确认兼容的生产旧版。

### 7.2 人工部署步骤（设计流程，不是当前可执行安装命令）

| 顺序 | 服务端 | 客户端 |
|---|---|---|
| P1 | 准备依赖及隔离测试镜像 | 准备依赖、确认 NBD 设备可用 |
| P2 | 部署已实现的 `nbd-server` | 部署已实现的 `nbd-monitor` |
| P3 | 部署审核后的正式 systemd 单元 | 部署审核后的 monitor 单元和原生 drop-in |
| P4 | 填写镜像、export 及监听配置 | 填写 monitor 配置和原生 nbdtab |
| P5 | daemon-reload，检查单元和配置 | daemon-reload，检查依赖和配置 |
| P6 | 启动控制/数据 socket 和 scan timer | 通过原生 nbd@ 建立连接 |
| P7 | 检查 Run 与 Session 关联 | 检查设备，挂载测试文件系统，执行受控读写 |
| P8 | 观察退出与 Run 档案 | 停止上层业务，卸载，再停止原生 nbd@ |
| P9 | 确认旧资源释放及 Journal 中的退出记录 | 重新连接，验证数据及新轮关联 |

按现有根文件系统映射目录进行最小人工部署，不开发安装器。仓库直接提供正式文件名，无需转换后缀；相应实现与单元通过审核后，按目标环境填写配置并部署到隔离验收环境。不允许直接复制整个 v0.0.1 基底到生产根目录；特别禁止在活动挂载期间替换或重启 monitor、原生 nbd@ 或 export 服务。

部署失败时停止在隔离环境中诊断，保留证据。未确认旧资源安全释放，不继续启动新导出、不覆盖镜像。历史生产版本可从 `archive/v0.4.2-M0` 获取；回退应在安全停机且确认无活动连接后进行，不能混用状态文件及协议。

## 8. 最小实机接入契约 MD01～MD15

| 编号 | 契约 |
|---|---|
| MD01 | 使用原生 nbd-client 与 qemu-nbd，不重新实现 NBD 数据通道。 |
| MD02 | 使用 systemd 管理生命周期。 |
| MD03 | 数据通道与控制通道独立。 |
| MD04 | 控制通道不依赖旧 export 进程存活。 |
| MD05 | 首验限定单资源、同一时刻单连接，使用两台受管客户端验证竞争。 |
| MD06 | 通过原生单元取得启动与退出事实，可靠关联本轮身份。 |
| MD07 | 实机接入层不得重复实现核心状态机。 |
| MD08 | 保留上层安全卸载、原生 detach 的基本顺序；缺失或异常须如实记录。 |
| MD09 | 首个版本不实施主动补做 detach 和自动 Reset。 |
| MD10 | 首个版本不实施自动快照及其它镜像维护。 |
| MD11 | 客户端仅使用临时状态和 Journal。 |
| MD12 | 服务端仅使用本次开机的临时状态和 Journal。 |
| MD13 | 不新增常驻组件及生产依赖。 |
| MD14 | 标准路径、最小配置、人工部署。 |
| MD15 | 云端尽量消化可验证的问题，本地完成真实环境验收；不建立独立云端自动化工作项目。 |

实机验收应验证 MD01～MD15 和 §2.2 的功能裁剪。待验事项见 §11。

## 9. 验收与研发分工

### 9.1 云端可消化的验证

不单列正式自动化工程，不引入 CI；在研发当次环境能力允许时，尽量直接验证实际 Bash 代码。可使用临时隔离目录、样本、替代底层命令和真实 loopback TCP 等方式。

| 验证范围 | 要求 |
|---|---|
| 配置/消息/原生执行记录解析 | 正常、非法、缺失、冲突、unknown 等边界。 |
| Close Exchange | 首版成功路径、Session 和 Run 匹配、冲突报告、末次 ACK 丢失及保存失败。 |
| 时间 | 内部截止、不同计时起点、单次请求阻塞、最终确认窗口。 |
| 并发与状态 | 锁、原子保存、新旧 Run 隔离、冻结快照、迟到补记。 |
| 异常路径 | 注入 A1/A2/A3 事实及控制通道故障，验证处理而非声称复现真实成因。 |
| systemd 模板 | 环境允许时进行离线语法及依赖审查，不替代真实生命周期验收。 |

验证结果应注明真实执行、模拟或未测试。云端不能取得的真实 NBD 内核、完整 systemd、QEMU 与文件系统联动证据由实机补足，不将模拟通过视作实机通过。

### 9.2 实机验收矩阵

| 编号 | 验收项目 | 通过条件 |
|---|---|---|
| D01 | 服务端监听 | 控制/数据 socket 与 scan 正常启用，数据连接触发正确导出。 |
| D02 | 原生连接 | 原生 nbd@ 正常建立测试 NBD 设备。 |
| D03 | 双端关联 | 原生 Invocation、Session、Run 正确关联；无历史记录冒用。 |
| D04 | 上层业务 | 测试文件系统正常挂载、读写、卸载。 |
| D05 | 原生退出事实 | 原生执行记录及 post-stop 设备事实可可靠取得，缺失如实标注。 |
| D06 | 阶段切换 | 正常 heartbeat 切换到 close；无退出阶段回退。 |
| D07 | 正常交接 | 唯一成功路径上的退出事实齐全，服务端保存后返回 `complete`。 |
| D08 | 异常报告 | A1/A2 或未知事实不会仅因设备未归零而被禁止发送；验证无主动补做。 |
| D09 | Run 记录 | Journal 可按 Run 核对结果、已有事实和失败原因。 |
| D10 | 下一轮 | 旧轮正常收口且资源释放后再次连接成功，Run 身份不同。 |
| D11 | 跨轮隔离 | 旧轮最终确认/重试不污染新轮，独立控制通道继续可用。 |
| D12 | 实际重启 | 验证 shutdown 时序与网络可用性，重启后旧 Session 失效，新连接重新准入。 |
| D13 | 安全保留 | 失败或超时后阻断新准入，核实释放并手动解锁后恢复竞争。 |
| D14 | 数据完整性 | 正常退出并重新连接后，预先写入的测试数据校验一致。 |
| D15 | 准入竞争 | 两台受管客户端竞争同一资源。只有获准者执行原生连接，且旧轮交接期间仍拒绝新准入。 |

此外，必须验证 §5 的真实停止预算及控制通道寿命。对 A1/A2/A3 真正异常成因的捕获，优先等待真实现场或使用隔离可丢弃资源。无法安全复现的场景标注为未实机验证。

### 9.3 最小可用性判定

正常实机闭环为监听 → 准入 → 原生连接 → heartbeat → 挂载读写 → 卸载 → 原生 detach → 交接与 Journal 记录 → 再连接与数据校验。

建议完成两个独立正常 Run，在 Journal 中核对各自记录。D12 重启链路单独验证。核心异常与终止规则先在可控环境验证，真实异常专项结果分别记录。任何安全不变量失败均阻止部署验收通过。

## 10. 指标分析的建设顺序

第一个可运行闭环以服务端的逐轮 Journal 记录和安全再连接为验收终点。后续可从长期 Run 档案经服务端只读导出接入 Prometheus 和 Grafana，以独立 Run 进行逐轮分析。

后者是总体目标，暂不作为第一个实机接入闭环的前置依赖。指标导出不增加客户端 exporter，不改变 NBD 连接/退出动作，不先行冻结指标名、标签或历史保留窗口。

## 11. 实机验收待确认

1. 在目标机核验原生 hook 的 Invocation ID 和 `ExecStop` 证据、真实启停顺序、关机时的网络与控制 socket，以及内核 NBD 和测试文件系统联动。
2. 按 §9 验证受管客户端竞争、唯一成功路径、失败阻断、人工解锁和整机重启。隔离 TCP 用替身验证了脚本流程。使用 `qemu-io` 已通过两轮真实 QEMU/QCOW2 写入与重连读回，交接采用模拟的客户端事实及显式传入的服务退出信息。
3. 审核实机测试用配置和正式单元部署方式。
